## Verified issues (medium and above)

### ED-1 · High · Redaction blur written to the file is much weaker than the preview shows

- **Where:** `src-tauri/src/shot.rs:139-210`, `src-tauri/src/shot.rs:633-661`, `src/components/ShotAnnotate.tsx:1063`, `src/components/ShotAnnotate.tsx:1079-1081`, `ShotViewer.tsx:1107`, `shot.rs:129-134` (+3 more)
- **Verification:** partial (impact: partly confirmed; reachability: partly confirmed; code: confirmed)
- **Also reported as:** EF-8 (Blur preview (CSS Gaussian) and saved blur (single box pass) differ; file leaks…)

**What verification found:** The saved PNG uses a single box pass per axis, while the preview is an equal-variance Gaussian, so the WYSIWYG promise does not hold. The danger is not that the file shows readable ghost strokes; looked at directly, it is if anything less legible than the preview. The danger is that a single box blur keeps 6-22% of contrast at text-stroke frequencies, well above 8-bit quantisation, so the redaction can be inverted. At the default radius (8 at 1080p, 16 at 4K), anyone holding the shared PNG can recover small text with a standard Wiener or least-squares deconvolution: the box PSF is trivially known or estimated, and the unblurred pixels around the rectangle are kept in the file. The equal-variance Gaussian the user previews resists this far better. Brute-force against a known font is about equally effective against both kernels, so it is not the distinguishing risk. The doc-comment remark about Chromium edges is unverified and, if true, errs in the safe direction.

**Original claim:** The saved PNG gets a single box-blur pass per axis (`blur_rows(&patch, &mut across, pw, ph, radius); … blur_rows(&turned, &mut done, ph, pw, radius);` in shot.rs), while the preview is a CSS Gaussian of the same variance (`backdropFilter: blur(${sigmaOf(step.radius) * box.scale}px)` with `Math.sqrt((radius*(radius+1))/3)` in ShotAnnotate.tsx). Matching variance does not match legibility: a box kernel has sinc side-lobes, a Gaussian none. For r = 4/8/16 (the 1080p minimum and default) the box lets through about 22% of contrast at periods of 6.3/11.9/23 px versus about 3.5% for the equal-variance Gaussian (roughly 6x less) - exactly text-stroke and letter scale. So the UI hint "What you see here is what lands in the file" (ShotViewer.tsx:1107) is false in the dangerous direction. Additionally the Rust doc comment (shot.rs:129-134) saying the preview "blurs the whole picture and clips afterwards" is likely inaccurate: Chromium's backdrop-filter samples only within the element (mirror edges), so near edges the two differ the other way.

**Scenario:** A user blurs a 14 px password or e-mail at the default radius. The preview looks fully smeared, but the saved PNG keeps ghosted strokes that are readable, or brute-forceable against the known game/UI font.

**Fix:** Approximate a Gaussian with 3 box passes per axis keeping the variance: `r_i = ((1.0 + 4.0*r*(r+1)/3.0).sqrt() - 1.0) / 2.0`, rounded and >= 1; run `blur_rows` 3x each way and widen the margin to `3*r_i` (still O(n)). Consider a minimum radius tied to the rectangle height (e.g. >= h/4) or pixelate-then-blur, and offer a solid "redact" fill. Fix the doc comment.

**Verifier on the fix:** Three box passes per axis with r_i = (sqrt(1 + 4r(r+1)/3) - 1)/2 and a margin of 3*r_i is correct, stays O(n), and in my test it defeated the same Wiener attack. Round r_i up (ceil, min 1) rather than to nearest, or set sigmaOf to sqrt(r_i(r_i+1)), so the file is never weaker than the preview: rounding r=8 gives r_i=4, variance 20 vs 24. Then update the doc comments in shot.rs and ShotAnnotate.tsx and the hint text. It is not sufficient on its own. ## Reported, not independently re-verified

The original reviewer checked these against the code, but the independent verification pass was stopped before reaching them. Treat as likely, confirm before fixing.

- **ED-16 · Medium · External edits to the screenshot are silently overwritten on the next ClippiBoy save** — `commands.rs:539`  
  `edit_screenshot` rebuilds from the stored original (`image.png`) every time (commands.rs:539) without checking whether the main file was changed externally; the DB dimensions also go stale.  
  *Fix:* Record size and mtime (or a hash) of the last written file in shot.json; on mismatch warn, or adopt the external file as the new original.
- **ED-17 · Medium · Blocking sync commands marked #[tauri::command(async)] run on tokio workers** — `commands.rs`  
  `write_screenshot`, `copy_clip_image` and `take_screenshot` are sync fns with `#[tauri::command(async)]`, which (likely, per Tauri 2.11 macro behaviour) runs them on async runtime workers. They do blocking work there: PNG decode/encode, blur loops, `replace_file`'s sleep-retry (up to about 2.75 s), the blocking ffmpeg wait, and `Clipboard::open`'s sleeps.  
  *Fix:* Make them `async fn` and wrap the body in `tauri::async_runtime::spawn_blocking`.
- **ED-2 · Medium · Sidecars committed before the main PNG; several screenshot writes are not atomic** — `commands.rs:589-598`, `commands.rs:606-620`, `commands.rs:627-638` (+3 more)  
  In edit_screenshot the write order is `shot.write_png(&base_path)` (`File::create` truncates base.png in place), then `write_edit(...)` (shot.json), then `write_picture` (temp + `replace_file`, retried 10x then fails with "Is it open somewhere right now?"). The comment at commands.rs:555 ("Everything that can fail happens before the first byte is written") is not true for these three writes. `keep_original` copies to `image.png` with a plain `std::fs::copy`, and `write_under` writes `under.png`/`under.json` non-atomically as well.  
  *Fix:* Write all three to temp names first (`base.png.part`, `shot.json.part`, `<name>.<uuid>.new.png`). Then `replace_file` the main PNG (most likely to fail); only on success rename the sidecar parts (or remove base.png); on failure delete the parts. `keep_original`: copy to `image.png.part` and rename. `write_under`: same for under.png and under.json.
- **ED-3 · Medium · Save racing a file move or delete orphans the edited PNG and leaves the DB pointing at the unedited file** — `commands.rs:518`, `commands.rs:632-651`, `src/routes/Clips.tsx:327-336` (+3 more)  
  `edit_screenshot` reads `clip.path` once at the start (commands.rs:518) and writes to it about 0.5-2 s later; nothing locks the clip. Closing the viewer runs `for (const id of seen) if (left.has(id)) void fileClip(id);` (Clips.tsx), and `file_clip` moves the file (favorites or game folder) and updates the DB path. The viewer's close button, Escape after Discard, and the footer Delete button all stay enabled while `busy`.  
  *Fix:* Add a per-clip busy set in `AppState`: `write_screenshot` holds it; `file_clip` and `delete_clip` wait for it or skip. Re-read `lib.get(id).path` immediately before `replace_file`, inside the library lock. Disable Close and Delete while `busy`, or defer `fileClip` until the save resolves.
- **ED-4 · Medium · Editor usable before its edit store loads; failed load swallowed; save then drops crop/marks and misplaces blurs** — `ShotViewer.tsx:341-356`, `ShotViewer.tsx:426-448`, `ShotViewer.tsx:956` (+3 more)  
  The load is `api.screenshotEdit(id).then(...).catch(() => {})` and tools are enabled with `disabled={!inTauri \|\| broken}` with no check of `edit`. While `edit` is null: `full = clip.width` (the cropped size), `origin = {0,0}`, draw mode draws on `clip.path` (marks already baked in), and Save sends `write(edit?.crop ?? null, shapes)`, i.e. crop = null. If the load resolves late, `resetShapes(readMarks(loaded))` silently wipes whatever was drawn in the meantime.  
  *Fix:* Disable tools and Save until `edit !== null`; show the load error instead of swallowing it; have `write` refuse to run while `edit` is null.
- **ED-5 · Medium · Save's async continuation is not tied to the clip it started for; old edit lands on the next picture** — `ShotViewer.tsx:604-644`, `ShotViewer.tsx:1089`, `ShotViewer.tsx:1249` (+1 more)  
  After `await writeScreenshot(...)` the code runs `const loaded = await api.screenshotEdit(clip.id); setEdit(loaded); resetShapes(readMarks(loaded));` using the closure's (old) `clip`, with no check that the viewer still shows it. Discard is always enabled (1089) and the step/navigation buttons are enabled once `mode === "view"` (1249, 1259).  
  *Fix:* Keep `const shownId = useRef(id)` and bail out after each await when `shownId.current !== clip.id`. Better: have `write_screenshot` return the new `ShotEdit` directly.
- **ED-6 · Medium · Marks drawn while a save is running are silently discarded** — `ShotViewer.tsx:880-892`, `ShotViewer.tsx:632-638`, `src/components/ShotViewer.tsx:604-644` (+2 more)  
  AnnotateLayer stays interactive while `busy` (ShotViewer.tsx:880-892). When the save finishes, `resetShapes(readMarks(loaded)); … setMode("view")` (632-638) replaces everything drawn since Save was clicked.  
  *Fix:* Block input while `busy` (`pointer-events: none` overlay or BusyVeil), or snapshot `current.current` at save time and re-apply any newer shapes as unsaved.
- **ED-7 · Medium · PNG decompression bomb in read_png/read_rgba (allocation before any size check), reachable via friend-shared screenshots** — `shot.rs:455-472`, `shot.rs:676-689`, `shot.rs:105-108` (+1 more)  
  `read_png` allocates the frame buffer from IHDR alone: `let mut buffer = vec![0u8; reader.output_buffer_size()];` (shot.rs:455-472); png 0.17's `Limits` only cap row and chunk buffers, not this caller-allocated buffer. `read_rgba` (shot.rs:676-689) checks the layer's dimensions against the picture only after the full allocation and decode (`blend`, shot.rs:105-108). Received shared files go straight into the library (share.rs:633-692).  
  *Fix:* After `read_info`, reject anything with `w as u64 * h as u64 > 1<<28` (and dimensions > 16384), then allocate with `try_reserve_exact`. Give `read_rgba` the expected `(w, h)` and reject on mismatch before allocating. At receive time read the header and store the real dimensions.
- **ED-8 · Medium · Layer PNGs travel over IPC as JSON number arrays and are buffered by serde as Content** — `ShotViewer.tsx:1607-1624`, `types.ts:527`, `commands.rs:400-419` (+3 more)  
  `layerBytes` returns `Array.from(new Uint8Array(await blob.arrayBuffer()))`, so each byte becomes about 3.6 JSON characters plus a JS Number, stringified on the UI thread. On the Rust side `Step` is internally tagged (`#[serde(tag = "kind")] … Layer { png: Vec<u8> }`), so serde first buffers the whole object into `Content` (one ~32-byte `Content::U64` per PNG byte) and then copies into `Vec<u8>`.  
  *Fix:* Send layers as raw IPC bodies (`invoke("write_shot_layer", bytes, { headers: { id, index } })`, Rust reads `tauri::ipc::Request` -> `InvokeBody::Raw`), or at minimum base64 strings with `#[serde(with = "...")]` and an adjacently/externally tagged enum. Encode in a worker with `OffscreenCanvas.convertToBlob`.
- **ED-9 · Medium · Preview and save use full-resolution canvases per blur-separated run** — `ShotAnnotate.tsx:566-586`, `ShotViewer.tsx:609-618`, `src/components/ShotAnnotate.tsx:566-586` (+1 more)  
  Preview canvases are `<canvas width={width} height={height}>` at full picture pixels (ShotAnnotate.tsx:566-586). Every blur splits the layer runs, so N blurs mean N+1 canvases of 3840x2160 (33 MB each; 132 MB each at 8K) plus the draft canvas. Save allocates another N full-size canvases at once (`Promise.all(... layerBytes ...)`, ShotViewer.tsx:609-618); at 8K this can fail, and `getContext`/`toBlob` returning null throws and is swallowed (see the swallowed-failures finding).  
  *Fix:* Size preview canvases to `round(box.width*devicePixelRatio)` with `ctx.setTransform(scale…)`, repainting on zoom. Serialise `layerBytes` (or use OffscreenCanvas in a worker).
- **EF-1 · Medium · Header close button discards unsaved marks without asking** — `src/components/ShotViewer.tsx:749-758`, `src/components/ShotViewer.tsx:380-386`, `src/components/ShotViewer.tsx:580-583` (+1 more)  
  In ShotViewer, the header close button (the ✕ at ShotViewer.tsx:749-758) calls `close` directly, so it closes the viewer without the unsaved-marks check that the Escape path performs (ShotViewer.tsx:380-386, 580-583). This contradicts the comment at ShotViewer.tsx:184-188.  
  *Fix:* Route the header ✕ through a `requestClose()` that does `if (editing && unsaved) setAskingDiscard(true) else close()`. Optionally keep a draft of `shapes` per clip id in `sessionStorage` so a crash or update restart can offer "Restore unsaved marks?".
- **EF-18 · Medium · Sidecar shot.json has no version and parse failures silently become "no edit"** — `src-tauri/src/shot.rs:311-320`, `src-tauri/src/shot.rs:335-340`, `src/components/ShotAnnotate.tsx:192-194`  
  `shot.json` is `{crop: Rect\|null, marks: string}` with no version field (shot.rs:311-320). Old marks are recognised only by missing fields, e.g. `outline !== false` (ShotAnnotate.tsx:192-194), with such rules scattered. `read_edit` turns any parse error into "no edit" via `unwrap_or_default` (shot.rs:335-340). If a newer version's file is opened by an older build, the editor would show `base.png` (cropped) as if it were uncropped and could wipe the edit on the next save.  
  *Fix:* Sidecar v2: Rust `#[serde(default)] version: u32` (missing means 1) and `marks: serde_json::Value` with a reader that also accepts the old string; refuse to edit when `version > SUPPORTED`, returning `readOnly: true` instead of `unwrap_or_default`. TS `readMarks` accepts a string or array, then one `normalizeShape()` fills defaults. Migrate lazily…
- **EF-5 · Medium · Shortcuts stop working after a slider or colour field gets focus** — `src/components/ShotViewer.tsx:378`, `src/components/ShotAnnotate.tsx:713-718`  
  The global key handler skips every INPUT element, including `type=range` (ShotViewer.tsx:378). So once the thickness slider or the hex/RGB colour field has focus, Delete, Ctrl+Z and Escape are ignored. The drawing surface calls `preventDefault` on pointerdown (ShotAnnotate.tsx:713-718, line 718), which stops it from taking focus, so drawing on the picture does not take focus back and the slider keeps focus indefinitely.  
  *Fix:* Skip only text-entry fields (`input:not([type=range],[type=checkbox],[type=button])`, `textarea`, `[contenteditable]`). In `onDown`, blur `document.activeElement` when it is not the caption field.
- **EF-6 · Medium · "Remove all marks" saves immediately with no confirmation or undo** — `src/components/ShotViewer.tsx:1095-1104`, `src/components/ShotViewer.tsx:634`  
  The "Remove all marks" action (ShotViewer.tsx:1095-1104) writes the file at once without asking. Because undo history is reset on every save (`resetShapes` at ShotViewer.tsx:634), the marks are gone for good.  
  *Fix:* Add a confirmation (reuse `ConfirmDelete`), or make it undoable by keeping the previous `marks` string.
- **EF-7 · Medium · Marks are invisible while cropping** — `src/components/ShotViewer.tsx:439-441`, `src/components/ShotViewer.tsx:880-893`  
  In crop mode the crop ground is the untouched original (ShotViewer.tsx:439-441), and the marks layer is only mounted in draw mode (ShotViewer.tsx:880-892). The user therefore cannot see their marks while choosing a crop, even though the crop cuts through them.  
  *Fix:* Mount read-only `ShapeLayer`s and `BlurPatch`es in crop mode at the original's coordinates (`shift` by +origin).

## What is solid

- Clip ids are sanitised everywhere (`muxer::sanitize`: ASCII alphanumerics, everything else `_`) and every shot command looks the id up in the library first; no path traversal.
- Serde shapes match the TS types: `Step` is internally tagged; ShotEdit, Rect and Clip are camelCase.
- TS `markRect` matches Rust `rect_kept` exactly, including f32 vs f64 rounding (the .5 cases were checked).
- Zoom and pan maths in the viewer are correct.
- `blur_rows` is tested against a naive implementation.
- No `u32` width x height overflow is reachable.
- clipboard.rs: the `unsafe` in `put` is correct (frees the handle on lock or Set failure, size >= len), as are the `DROPFILES` layout and the DIB stride and padding.
- The edit model is non-destructive: `Shape[]` is kept as JSON beside the file and every save rebuilds the picture from the untouched original (commands.rs:484-599), so crop and marks are independent and "Undo crop" keeps the marks (ShotViewer.tsx:1174).
- The watermark cannot be removed by editing: every edit lays the clean area back and re-stamps a fresh watermark (commands.rs:540-545, 585-587), shrinking to the smallest legible size on small crops (`rect_kept` 94-125).
- Arrows, boxes, pen and text are painted by one `paint` routine on Chromium canvas for both preview and file (`layerBytes`), so antialiasing, line caps, fonts and text metrics cannot drift; not drawing text in Rust was a good call.
- Marks can be selected, moved, resized and restyled after placing; the hit test is generous and hollow frames only answer on their line so arrows inside frames stay pickable; moves are clamped inside the picture (ShotAnnotate.tsx:345-397, 785-803).
- Writes are crash-safe: `shot.json` goes through `.part` + rename (shot.rs:342-356) and the picture through temp + replace (commands.rs:627-638); nothing is written until everything that can fail has run (commands.rs:555-565).
- Watermark rectangle parity: Rust f32 `rect_kept` vs TS f64 `markRect` compared for heights 1-4399 against 19 widths each gave 0 mismatches; no drift today.
- A picture resized outside ClippiBoy is detected and edited as it is (shot.rs:402-420).
- HiDPI is handled correctly: layout uses CSS-pixel sizes (`clientWidth`) and canvases are kept at the picture's own resolution.
- `lib/lockdown.ts:29-47` blocks the browser's own Ctrl+S, Ctrl+=, Ctrl+- and Ctrl+0 with preventDefault only, so the editor is free to use those shortcuts.
- Existing accessibility basics: tool and crop buttons have `aria-pressed`, sections have `aria-expanded`, the text field has an `aria-label`, and reduced motion is respected on close.
- Undo is snapshot-based with gesture coalescing: a drag or one slider pull counts as one step (ShotViewer.tsx:281-294).
- Rust has unit tests for the sliding blur against a naive version, the blur margin, the crop clamp (shot.rs:709-823) and the watermark rectangles (watermark.rs:219-303).
- The WebView/Rust split is right for vector marks (it is wrong only for pixel-reading tools).
